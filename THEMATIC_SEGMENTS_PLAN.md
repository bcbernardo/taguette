# Plan: coding guided by thematic segments

## Vocabulary (used in the plan, the UI and the code)

| Term | What it is | Where it lives | Where it shows up |
|---|---|---|---|
| **Tag** | an analytic theme or code, in the qualitative-analysis sense (unchanged) | server (`tags`) | tags panel, highlight modal, suggestion menu |
| **Thematic segment** | one broad area covered by the semi-structured interview script: name, description and the script questions tied to it | server (`thematic_segments`, project level) | "Script & segments" panel |
| **Segment guide** | the set of the project's thematic segments | server | same panel |
| **Support document** | interview script, research questions, hypotheses | server (`support_documents`) | same panel |
| **Section** | a contiguous stretch of one document assigned to a thematic segment or to an emergent segment; one thematic segment can have several sections in the same document | browser (IndexedDB) | document "Segmentation" panel and separators in the text |
| **Emergent segment** | an off-script subject detected in a document; it joins the guide (`source:'emergent'`) when the document's highlights are saved and the user confirms (§4.8) | browser until confirmed, then server | "Segmentation" panel; after saving, also "Script & segments" |
| **Unit** | an argument unit inside a section; this is what becomes a highlight suggestion | suggestion session | brackets in the text |

The word "theme" is reserved for tags.

## Context

The current suggestions (`taguette/static/js/suggest.js`: TextRank, LexRank, YAKE, RAKE and k-means) do extractive summarization: they pick a few salient passages from the whole document. The reference coding (`2026-11-01_AIM 2026 Charity Interviews.sqlite3`, a 119-minute interview) is open and exhaustive:

- 119 highlights with a median of 70 words (IQR 40–112), covering ≈ 47% of the text;
- 102 tags, 1.4 per highlight, 56% used only once;
- the interviewer asks **41 substantive questions** (≥ 8 words, containing "?") for 14,700 interviewee words, i.e. ≈ 1 question every 360 words.

Top-k by salience is the wrong objective, and the existing codebook is not reused.

**Goal:** split each interview into sections, seeded by the project's script but flexible enough for tangents and spontaneous subjects. Within each section, cover all codable speech with argument units and propose tags from the codebook.

User decisions:
- The segment guide and the support documents live on the server and are generated by a more capable LLM with its own configuration. The sections of each document live in the browser.
- Script questions and sections do not map one to one.
- The per-document engine is embeddings plus a decision model (system 1). The fast LLM steps in **automatically**, and only in the ambiguous band.
- Each feature has its own decision client. They share only the provider, model and credential configuration (the `decisions` task) and the generic cache.
- The speaker plan is already implemented: this plan takes `sug_session.speakers` and `turn.speaker` as input.
- The segmentation parameters can be edited in the configuration screen.

## Architecture

```
PROJECT (server)
  support documents ──advanced LLM──► segment guide: [thematic segment]
                                             ▲ emergent segments confirmed on save
DOCUMENT (browser)                           │
  turns + speakers ─► windows ─► Viterbi labelling: thematic segment | "other"
                                  + system-1 decision on ambiguous windows
                      ─► sections (a thematic segment can recur; a long "other" run becomes an emergent segment)
                      ─► units per section ─► candidate tags (prototypes) ─► system-1 verification
                                                                           └─ ambiguous band: fast LLM, automatic
                      ─► suggestion session (brackets; proposed tags in each suggestion's menu)
```

## 1. Server: support documents and segment guide

They get their own tables. Reusing `documents` with a flag would make these files show up in the document list, in exports and in coding.

- **`taguette/database.py`** and a new Alembic migration:
  - `SupportDocument`: `id`, `project_id` (FK with CASCADE), `name`, `kind` (`script`, `research_questions`, `hypotheses` or `other`), `contents` (plain text), `created`.
  - `ThematicSegment`: `id`, `project_id` (FK with CASCADE), `position`, `name`, `description`, `guide_questions` (Text, one question per line), `source` (`guide`, `emergent` or `manual`), `created`.
  - `support_documents` and `thematic_segments` commands in `Command.TYPES`, following the `document_edit` pattern, for long-polling.
  - Include both tables in `copy_project` (`database.py:776`).
- **API** (`taguette/web/api.py`, routes in `taguette/web/__init__.py`):
  - `GET`/`POST /api/project/<p>/support_documents`. Upload reuses `convert.py` and stores only the text; pasted text is also accepted.
  - `DELETE /api/project/<p>/support_documents/<id>`.
  - `GET`/`PUT /api/project/<p>/thematic_segments`. PUT replaces the whole list in one transaction and validates the data.
  - Permissions: reading requires project membership; writing requires permission to edit the project metadata.
- **Tests** in `tests.py`: CRUD, validation, permissions, project copy and cascade.

## 2. Advanced LLM and guide generation

- **`config.js`**: new `reasoning` task (`kind: 'chat'`) with an "Advanced LLM" tab, following the pattern of the `llm` and `segmentation` tabs. It asks for a long-context model. Generalize `tagAiLLMConfig(taskId)` (`tags-ai.js:302`) if not already done, and reuse `tagAiChat` (`tags-ai.js:315`).
- **"Script & segments" panel** (project level):
  - support documents: upload, paste text, remove;
  - **"Generate guide with AI"**: one call with the **full text** of the support documents and with the codebook (tag names and definitions, so the LLM does not mix the two up). It returns `{segments:[{name, description, guide_questions:[...]}]}`. The instructions ask for **analytic** thematic segments, not a copy of the questions: several questions can fall under the same thematic segment, and follow-up questions stay with their main question;
  - review: edit, reorder, merge, delete, add; "Save" calls the PUT;
  - `emergent` segments are marked, with the number of documents they appeared in.

## 3. Parameters in the configuration screen

The **"Segmentation"** tab of the configuration screen (the one created by the speaker plan) gets a new section, **"Thematic segments and units"**. Values are stored in `taguConfig().segmentation_params`, and each one has a "restore default" button.

Greek letters exist **only in the code**. On screen, each parameter has a plain-language label and help text right below it, saying what happens when the value goes up or down.

| On-screen label | Variable | Default | On-screen help text |
|---|---|---|---|
| Maximum window size (words) | `window_max_words` | 80 | "Long turns are split into windows of this size before being compared with the thematic segments. Smaller windows catch subject changes within a single turn, but each window on its own is noisier." |
| Minimum section size (codable words) | `section_min_words` | 150 | "Sections smaller than this are absorbed into the most similar neighbour. Raise it if the interview comes out too fragmented; lower it if short subjects are disappearing." |
| Minimum emergent segment size (words) | `emergent_min_words` | 250 | "An off-script subject only becomes an emergent segment if it lasts at least this long; below the minimum it is absorbed into the neighbouring section." |
| Suggested unit size (min/max words) | `unit_min_words`, `unit_max_words` | 25 / 150 | "Size limits for highlight suggestions." |
| Unit granularity | `τ` | calibrated (§9) | "The higher it is, the more readily a suggestion is cut when the subject shifts slightly, producing smaller and more numerous suggestions. Also adjustable with the suggestion session slider." |
| Tags checked per suggestion | `K` | 8 | "How many of the tags most similar to the passage are sent to the decision model for checking. More tags find less obvious codes, but make each request slower." |
| Minimum confidence to tick a tag | `θ` | 0.6 | "Tags at or above this confidence come pre-ticked in the suggestion menu. Below it, they appear unticked." |
| Uncertainty band (checked by the fast LLM) | — | 0.4–0.6 | "Tags whose confidence falls in this band are automatically re-checked by the fast LLM, if one is configured." |
| Advanced: tolerance for off-script subjects | `κ` | calibrated (§9) | "The higher it is, the more readily a passage that looks little like the script is marked as a new (emergent) subject instead of being fitted into the closest thematic segment." |
| Advanced: resistance to switching segments | `λ` | calibrated (§9) | "The higher it is, the more the algorithm prefers to stay in the current segment, producing fewer and longer sections; brief tangents no longer become sections of their own." |

The number of sections is **neither fixed nor estimated** from interviewee word counts. It comes out of the labelling: how many thematic segments appear, how often the interview returns to each one, and how many emergent segments arise. The parameters above only limit fragmentation. For the reference interview, the expectation is close to the 41 substantive questions minus the follow-ups, i.e. **dozens of sections**, not 12. That number is used as a check in §9.

## 4. Document segmentation (browser, new `segments.js`, prefix `seg`)

1. **Windows**: turns from `sugBlocks()` with `turn.speaker`. Long turns are split up to the maximum window size (`sugSplitSentences`). Windows from excluded speakers (the interviewer) count as **cues** (the question asked), not as content.
2. **Thematic segment prototypes**: embedding of `name + description + script questions`. Once the project has documents that were already segmented, the centroid of the real highlights that fell in sections of that thematic segment is added as well. Uses `sugEmbed` with the L1/L2 cache.
3. **Sequential labelling (Viterbi)**:
   - the states are the thematic segments plus an `other` state;
   - emission = cosine(window, prototype); `other` emits the threshold κ;
   - for interviewer windows, emission uses similarity with `guide_questions`, which is a strong switch signal;
   - transition = a penalty λ per switch, **with no imposed order**, so a thematic segment can come back after a tangent.

   Contiguous runs become sections. Sections below the minimum codable word count are absorbed into the most similar neighbour.
4. **System-1 tie-break** (a client of its own for this feature): on windows where the two best states are close, one `choice` question whose criteria are the top 3 thematic segments (with descriptions) plus `other_topic`. The `state` contains the window, the interviewer's latest question and the previous window. The returned probability replaces the emission and Viterbi runs again.
5. **Emergent segments**: an `other` run above the minimum becomes the section "Emergent n". The fast LLM (`llm` task) **automatically** receives the **full text of the section** (these are short and fit in any model) and returns a **proposed definition**:
   - a name;
   - a description;
   - a **rephrased question**, written in the register of an interview script, generic, without proper names or case details.

   Until the document is saved, this proposal lives only in the browser. §4.8 explains how it reaches the server.
6. **Section label**: the name of the thematic or emergent segment, followed by the **opening question**, i.e. the literal text of the interviewer turn that starts the section, when there is one, truncated to a single line. It is extracted from the document deterministically, with no LLM. It lets the user check the assignment at a glance: if the question does not match the thematic segment, the assignment is probably wrong.

   **The opening question is never persisted on the server.** It is recomputed from the transcript and kept only in the local section cache in IndexedDB. What goes into the guide is the rephrased question (item 5), and only after the review in §4.8.
7. **"Segmentation" panel** (next to the document):
   - list of sections with their label, a selector to change the thematic segment (including "Emergent" and "new…"), a coverage bar and the number of suggestions;
   - separators in the text painted by CSS (`attr(data-seg-label)`), without polluting the offsets;
   - actions: drag a boundary (snapping to the start of a turn), split, merge;
   - **script coverage**: which thematic segments of the guide appeared and which did not;
   - on an emergent section, the selector offers "merge into an existing thematic segment" and "discard as emergent" (the section is absorbed by its neighbours);
   - persisted in IndexedDB per document and text hash. After a transcript edit everything is recomputed, and manual adjustments are inherited for turns whose text did not change (`sugRebuildAfterReload`).
8. **Persisting emergent segments**: there is no separate "promote" button. An emergent segment joins the project guide (`source:'emergent'`) **when the document's highlights are saved**, and that is the only path.
   - The session stop modal (`sugStopDialog`), after the user chooses to save and if the document has emergent segments, shows a confirmation step: **"X new emergent segments will be created in the project guide. Confirm?"**.
   - Each emergent segment appears on its own row with name, description and rephrased question, **all editable**. If one is similar to an existing thematic segment (cosine ≥ 0.85, for example an emergent segment another interview already created), the row suggests "merge into «Y»" instead of creating a new one.
   - The buttons:
     - **Yes**: saves the highlights and creates the segments (PUT of the guide with the new ones appended);
     - **Back**: returns to the session without saving anything;
     - **Discard**: saves the highlights **without** creating the segments. The emergent segments stay as local sections of this document, and the dialog shows up again on the next save.
   - After the PUT, the local sections point to the new server ids.

## 5. Argument units (inside each section)

1. Sentences from turns of included speakers. Backchannels (`sugIsBackchannel`) from another speaker are transparent.
2. **Greedy cohesion**: a unit grows while `cos(sentence, centroid) ≥ τ` and it stays under the maximum word count. It is cut at a new substantive interviewer turn. Short units are merged into a neighbour.
3. Ambiguous joins: a `choice {continues, new_point}` decision, with the section label in the `state`.
4. **Coverage first**: nothing is dropped for low salience. The only units removed are those a `{substantive, small_talk}` decision marks as small talk with confidence ≥ 0.7.

## 6. Codebook tags (suggestion session only)

1. **Tag prototypes**: embeddings of `tagSearchText(tag)` (`taguette.js:1078`) and of the existing highlights (`tagAiFetchHighlights`, `tags-ai.js:924`). Highlights overlapping the unit itself are left out.
2. **Score**: `s(u,t) = max(cos(u, definition_t), mean of the 2 highest cos(u, exemplars_t))`. Tags that have already co-occurred with the same thematic segment in other documents get a small bonus.
3. **System-1 verification**: the top-K candidates go in one request per unit, with one `{applies, does_not_apply}` question per tag (name, definition and one example). The `state` contains the unit, the section label and the opening question.
4. **Ambiguous band → fast LLM, automatic**: tags whose `prob` falls in the ambiguous band are re-checked by the `llm` task, in one call per section that bundles that section's ambiguous units. A JSON `applies: true/false` answer replaces the decision. There is no button. Without a configured LLM, the system-1 decision stands.
5. **Layout**:
   - suggestions keep today's brackets; the badge shows the number of proposed tags;
   - clicking a suggestion opens the context menu (`sugShowSuggestionMenu`), which gets a **"Suggested tags"** section: checkboxes with name and confidence. Tags with confidence ≥ θ come ticked; the other candidates appear unticked, in grey;
   - "Save as highlight" stores the unit with the ticked tags (`staged.tags`), and the tag picker for staged highlights (`sugShowTagPicker`) lists the suggested tags first;
   - **a unit with no tag above θ**: the section simply does not appear. To create a new tag, the flow is today's (the highlight modal with AI name suggestions).

## 7. Separate decision clients per feature

`segments.js` holds three builders, each with its own questions, `state`, parsing and post-processing: the window's segment (§4.4), continuity and small talk (§5), and tag application (§6). The speaker client is not touched.

What is shared: resolution of the `decisions` task (`taguTaskResolve`) and the cache (`sugTextKey`, `sugIdbGetMany` and `sugIdbPutMany`). A small transport function (fetch, auth and concurrency pool) lives inside `segments.js`.

## 8. Integration with the suggestion session

- `sugComputePane` accepts an `algo.run` that returns a Promise.
- A new `'segmented'` algorithm ("Segment-based coding") is added to `SUG_ALGOS`.
- Candidates gain `tags:[{id, name, conf}]` and `section_id`.
- In this mode the slider controls θ and τ, not a top-k.
- Per-section coverage in the Segmentation panel, with "Refine this section" (lowers τ and θ for that section only).

## 9. Evaluation and calibration against a hand-coded document

This is a rarely used feature, so it stays **out of the main layout**: an **"Evaluate against existing highlights"** button at the bottom of the **Segmentation tab of the configuration screen**, right below the parameters it helps calibrate. It is enabled only when the open document already has highlights, and the results appear in the tab itself. The button runs the whole pipeline on the open document as if it were uncoded:

- the real highlights are hidden;
- the document's own highlights are removed from the tag exemplars, so the algorithm cannot "copy" the answer;
- the suggested units and tags are compared with the real ones.

The tab shows (and logs to the console):

| Metric | Question it answers |
|---|---|
| Unit recall: % of real highlights with ≥ 50% of their bytes covered by some suggestion | did it find what you coded? |
| Byte recall and precision | did it cover the right amount of text, without suggesting too much? |
| Suggestion size (median and IQR in words) vs. 40/70/112 | are the units the size of yours? |
| Tag hit@k: the real tag is among the k most confident tags of the unit covering the highlight (only tags with ≥ 2 uses in the project) | is the codebook reused correctly? |
| θ calibration: precision of the pre-ticked tags | do the tags ticked by default deserve to be ticked? |
| Sections: count, % in `other`, script coverage | is the segmentation granularity plausible (dozens for the reference)? |

**Calibration** uses a second button in the same tab, "Test parameter combinations", which tries a small grid of τ, κ, λ and θ values and suggests the ones with the best unit recall at a minimum precision. It is cheap because the embeddings and decisions are already cached, and each new combination only requests what was never asked before. The winners appear next to the current values, with an "Apply" button.

For the reference interview, its script has to be uploaded as a support document. The initial targets are: unit recall ≥ 0.7, median size between 50 and 90 words, and hit@3 ≥ 0.5.

## Implementation notes (as built)

Where the implementation refines the plan:

- **Files.** `segments.js` is split in three, all sharing the `seg` prefix: `segments.js` (pure pipeline, no DOM or network: windows, Viterbi, sections, units, tags, question builders and parsers, evaluation; runs under Node), `segments-ai.js` (Jev/Laya decision transport, fast/advanced LLM calls, server API helpers, exemplar fetching) and `segments-ui.js` (panels, persistence, session hooks, emergent confirmation, evaluation tab). The pipeline receives its embedder, decision and LLM functions as injected dependencies.
- **Decisions task.** The speaker feature had removed the `decisions` tab. It is restored, with the `laya` local service, and is the system-1 model used here.
- **Model-agnostic parameters.** Raw cosine thresholds depend on the embedding model, so the parameters are relative to each document. `τ` and `κ` are quantiles: of the sentence-to-unit similarities and of the per-window best segment scores. Emissions are z-scores, and `λ` is in z units. Switching segments costs `λ` at a turn start, `0.25·λ` at a substantive interviewer question and `1.5·λ` mid-turn. Defaults: `τ` 0.25, `κ` 0.15, `λ` 2. Values are stored in `taguConfig().segmentation_params`.
- **Requests.** One decision request per unit carries the small-talk question and the K tag questions. Ambiguous windows are capped at min(120, 20% of content windows) and continuity questions at min(80, 5% of sentences). On the reference interview this gives about 320 decision requests, 3–4 embedding batches and about 40 fast-LLM calls.
- **Evaluation.** Units tile all codable speech, so unit recall is saturated (≈ 1.0). The tab therefore also reports IoU matching (a unit and a highlight with IoU ≥ 0.5) and the recall/F1 of the pre-ticked tags. "Test parameter combinations" optimizes IoU F1 for `τ`, `κ` and `λ`, and ticked-tag F1 for `θ`.
- **Learning from saved highlights.** When suggestions are saved, the unit vectors and tags are recorded per thematic segment in IndexedDB. Later analyses use them as prototype centroids and as the tag/segment co-occurrence bonus. The document under evaluation is excluded.
- **Security.** JSON embedded in the project page's inline script is now escaped (`</script>` in a segment name could otherwise break out).
- **Not validated yet.** The defaults were checked offline only (`scripts/segments_eval_reference.js`), with a TF-IDF/LSA stand-in embedder, a synthetic guide and mock decisions. They should be recalibrated with real models in the configuration tab.
